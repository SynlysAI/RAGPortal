# 知识库申请审批设计

**目标：** 普通用户可申请新知识库，管理员审核通过后记录申请结果，管理员再在 WeKnora 手工创建知识库并选择模型参数。

**方案：** 申请端只收集必要信息，例如知识库名称、描述、申请理由。审核端显示申请信息与审批结果，管理员无需选择模型参数。后端统一维护一份知识库创建默认模板，避免把 WeKnora 的实现细节暴露给用户，也避免后续模型/存储配置变动影响申请表单。

**技术栈：** FastAPI、SQLAlchemy、SQLite、React、TypeScript、WeKnora HTTP API

---

## 需求边界

- 普通用户只能提交“申请创建知识库”，不能直接创建。
- 申请单只包含最小必要字段。
- 管理员可审核通过或拒绝。
- 审核通过后只记录申请通过状态，不自动调用 WeKnora 创建。
- 管理员需在 WeKnora 中手工创建知识库并选择模型参数。
- WeKnora 创建完成后，新知识库会随知识库列表同步出现并可上传。
- 申请信息不包含模型配置。

## 申请字段

- 知识库名称：必填。
- 知识库描述：可选。
- 申请理由：可选，但建议填写。

## 审批字段

- 状态：`pending`、`approved`、`rejected`、`created`、`failed`。
- 审批人信息。
- 驳回原因。
- 创建后的 `kb_id` 和 `kb_name`。
- 创建失败原因。

## 后端行为

- 用户提交申请后，落本地申请表。
- 管理员点击通过后，只记录申请已通过。
- 具体知识库创建动作在 WeKnora 中手工完成。
- 若管理员拒绝，申请改为 `rejected`，不调用 WeKnora。

## 前端行为

- 上传页提供“申请新知识库”入口。
- 申请表单只展示必要字段。
- 管理员侧提供申请列表和审批动作。
- 申请通过后，管理员完成手工创建并刷新页面后，普通用户可在知识库下拉框里看到新库。

## 非目标

- 不做完整工单系统。
- 不做多级审批。
- 不让普通用户选择模型、向量库或存储配置。
- 不做复杂通知系统，先以页面状态为准。
